## versionCode 的坑（Flutter 3.41.9+）

### 现象

服务端 API 返回 version=1.2.30, build=2230，但 Android 安装时提示"已安装更高版本"，无法安装。

### 原因

Flutter 3.41.9+ 在 build split APK（`--split-per-abi`）时，会自动给 versionCode 加上 ABI offset：

| 构建方式 | 命令 | versionCode 公式 | 1.2.30+300 实际值 |
|---------|------|-----------------|-------------------|
| Universal（默认） | `flutter build apk --release` | = build | 300 |
| arm64 split | 自动生成（Gradle task） | build + 2×1000 | 2300 |
| armeabi-v7a split | 自动生成 | build + 1×1000 | 1300 |
| x86_64 split | 自动生成 | build + 4×1000 | 4300 |
| arm64 专用 | `flutter build apk --release --target-platform android-arm64` | = build（无 offset） | 300 |

**问题出在：** 用户手机上安装的是 split APK（versionCode=2223，即 223+2×1000），但服务端上传的是无 offset 的 universal APK（versionCode=300）。Android 系统安装器只看 versionCode 整数，300 < 2223，所以拒绝降级安装。

### 解决方案

**方案一：统一使用 universal 构建（推荐）**

```bash
flutter build apk --release
```

versionCode = build 号，无 ABI offset。上传此 APK 即可。

**方案二：使用 arm64 专用构建**

```bash
flutter build apk --release --target-platform android-arm64
```

生成的 `app-release.apk` 只含 arm64 代码，但 versionCode 仍然无 offset（= build 号）。

**方案三：如果必须用 split APK**

确保 build 号足够大，使带 offset 后的 versionCode 仍大于已安装版本。公式：

```
最终 versionCode = build + ABI_OFFSET

ABI_OFFSET:
  arm64-v8a:   2000
  armeabi-v7a: 1000
  x86_64:      4000
```

### 验证方法

打包后用 aapt 检查 APK 内部的 versionCode：

```bash
aapt dump badging app-release.apk | findstr versionCode
```

### 推荐流程

1. 改 pubspec.yaml 版本号，如 `1.2.30+2230`
2. 执行 `flutter build apk --release --target-platform android-arm64`
3. 验证 versionCode
4. 上传到 NAS `/tmp/`，然后通过 curl 或管理页面上传 release
5. 手机端检测更新

## 从 split-per-abi 切到单 arm64 的过渡注意

**2026-06-13 起，build_release_apk.py 已统一改为 `--target-platform android-arm64`** —— APK 体积从 ~110MB 降到 ~66MB，且不再有 ABI offset 的隐式偏移。

### 切换时的版本号策略（一次性）

切换那次 build 号必须**大于上一次 split 包带偏移后的真实 versionCode**，否则 Android 报"已安装更高版本"。例如：

- 切换前最后一次 split 包：`pubspec 1.2.34+2234` → 实际 versionCode = `2234 + 2000 = 4234`
- 切换后第一次单 arm64：build 必须 > 4234。我们当时取 `1.2.35+4235`（versionCode = 4235）。
- 之后保持单 arm64：每次 build +1 即可。

### 上传后用 aapt 必查

```powershell
$aapt = "C:\Users\Administrator\AppData\Local\Android\sdk\build-tools\28.0.3\aapt.exe"
& $aapt dump badging <APK 路径> | Select-String 'versionCode|name='
```

`versionCode=` 必须等于 pubspec 里 `+` 号后的数字，否则你弄错了构建模式。

## PackageInfo 缓存的坑（Dart 进程内不刷新）

### 现象

APP 检测到有更新 → 用户点更新 → 下载完成 → 唤起系统安装器 → 安装器报 **"已安装相同版本"**，但 APP 仍持续显示"有新版本"。重启 APP 后才正常。

### 根因

`package_info_plus` 在 Android 端的 `PackageInfo.fromPlatform()` 是 **Dart isolate 静态缓存**：进程内只调一次平台层。一旦用户在原来的 APP 进程内装完新版（系统会临时挂起 APP 让安装器接管，再返回），Dart 端拿到的还是**旧 versionCode**。

由此触发死循环：
- 服务器最新 build = 4236
- APP 已装 4236 但 Dart 缓存里还是 4235
- isNewerThanInstalled 判断 4236 > 4235 → 弹"有更新"
- 下载、调安装器
- Android 看 manifest 4236 == 已装 4236 → "已安装相同版本"

### 修复（2026-06-13 已落地）

在 `MainActivity.kt` 暴露 `currentVersionCode()` MethodChannel，每次 `isNewerThanInstalled` 都直接问 `PackageManager.getPackageInfo(packageName, 0).longVersionCode`（不缓存）。

### 升级老版本注意

老版本 APP（1.2.36 及以前）有这个 bug。**用户从老版本升到 1.2.37+ 的那一次仍可能踩坑**：升级提示触发了 → 下载装上 1.2.37 → 系统安装器看 4237 > 4236 → 接受。装完后老 APP 进程被新版替换，从此 Dart 每次都取实时 versionCode，不再有问题。

如果用户卡在那一次升级（看到"已安装相同版本"），需要他**完全杀进程重开 APP**，再点检查更新即可。

## 几个易混淆的 build 号

| 字段 | 出处 | 含义 |
|------|------|------|
| `pubspec.yaml` 中 `version: X.Y.Z+N` 的 N | pubspec | "想要的" build 号 |
| Flutter `flutter.versionCode` | gradle 内置 | 与 pubspec 的 N 相同 |
| split-per-abi 包的 manifest versionCode | aapt 实测 | N + ABI_OFFSET（坑） |
| 单 arm64 / universal 包的 manifest versionCode | aapt 实测 | = N（无偏移） |
| 上传服务器时 `--build` | upload_release.py 参数 | 必须等于 pubspec 的 N |
| 服务端 release 表 `build` 字段 | server.js | 上传时传入的 N |
| `PackageInfo.buildNumber`（Flutter 端） | package_info_plus | 已装 APK 的 manifest versionCode（实数） |
| Android 系统安装器比较 | OS 内置 | 已装 APK 的 manifest versionCode |

**关键：** 服务端 release.build 是 N（pubspec 的 build），但 PackageInfo.buildNumber 是 manifest 实测 versionCode。用 split-per-abi 时这两者不相等，会把"是否有新版本"的判断搞错。**这就是为什么我们必须用单 arm64 / universal**——保证 N == manifest versionCode == PackageInfo.buildNumber，三者完全等同，比较才简单。
